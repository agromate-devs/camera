# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The webcam ("broadcaster") component of the Agromate/AgroSmart system. A Python process captures a local camera and streams it over WebRTC (aiortc) to viewers, using an MQTT broker for signaling. The sibling projects `../agrosmart`, `../agromate_mobile_app` and `../agromate_server` (see `agrosmart.code-workspace`) hold the viewer app and the server that registers webcams, manages MQTT ACLs and issues TURN credentials.

## Commands

There is no build step, linter config, or test suite.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt        # aiomqtt, aiortc, aiohttp

# Generate credentials + camera_config.json (then add the webcam in the Agromate app with the printed username/password)
python setup_mqtt_client.py --broker <host> --server-url http://<host>:3000 [-p 1883] [-o camera_config.json]

# Run the broadcaster (reads ./camera_config.json from the CWD)
python main.py [-l DEBUG] [-v 640x480] [-vd /dev/video0] [-vf v4l2]
python main.py --test                  # streams a remote sample MP4 instead of a camera
```

Device/format defaults are Linux (`/dev/video0`, `v4l2`). Equivalents used on other platforms (from `README.md`): macOS `-vd default:none -vf avfoundation`; Windows `-vd "video=Integrated Camera" -vf dshow`.

## Architecture

`main.py` runs two concurrent asyncio tasks:

1. **MQTT signaling loop** (`main`) — connects with the webcam's credentials and subscribes to `webrtc/<CLIENT_ID>/signaling`. `CLIENT_ID` is the webcam username from the config (`cam_xxxxxxxx`); it is simultaneously the server-side webcam ID, the MQTT username/client identifier, and the `senderId` on every outgoing message. Messages whose `senderId == CLIENT_ID` are ignored (own echoes).
2. **TURN credential refresher** (`turn_updater`) — calls `GET <server_url>/turn` with HTTP Basic auth (same username/password as MQTT), stores `{username, password, ttl, urls}` in the module-level `turn_credentials` dict under `_turn_semaphore`, and sleeps until `ttl - 120`s (or `ttl - 10` if ttl < 240; 60s retry on failure).

Signaling flow (also described in `camera_protocol.md`):
- Viewer publishes `register-viewer` on the main topic with `target=CLIENT_ID` and `topic=webrtc/<CLIENT_ID>/<viewerId>`. The broadcaster only accepts a topic that exactly equals `get_topic(senderId)`, subscribes to it, and replies `viewer-registered` on the main topic.
- Viewer sends an `offer` on its reserved topic → `handle_offer` creates one `RTCPeerConnection` + `MediaPlayer` per viewer (stored in `pcs` keyed by viewer id), using STUN (Google) + TURN only if credentials have been fetched, publishes the `answer`, and trickles its own ICE as `ice-candidate` messages on the viewer topic.
- On `failed`/`closed` connection state the pc is closed, removed from `pcs`, the viewer topic is unsubscribed and media tracks are stopped.

Things to be aware of when changing `main.py`:
- `CLIENT_ID`, `MQTT_TOPIC` and `args` are module globals assigned inside the `if __name__ == "__main__":` block; `main()` reads `args` directly, so the module isn't usable as an import without refactoring.
- `camera_protocol.md` says the viewer sends ICE candidates, but the message loop only dispatches `register-viewer` and `offer` — incoming viewer `ice-candidate` messages are currently not handled.
- `index.html` is an old standalone browser viewer that uses the legacy `webrtc/signaling` topic on `test.mosquitto.org`; it does not follow the current protocol.

## Config and secrets

`camera_config.json` (`broker`, `port`, `username`, `password`, `server_url`) is generated by `setup_mqtt_client.py`. `camera_config.json`, `mosquitto.json` and `client_id.txt` hold real credentials and are untracked — don't commit them (only `__pycache__` is in `.gitignore`).
